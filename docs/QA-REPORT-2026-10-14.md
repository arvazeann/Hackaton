## D. Bugs and findings

### BUG-01 — Medium — Google callback URI is not authorized

- Reproduction: use the Google sign-in button on the reported Vercel deployment.
- Expected: Google returns to the Auth.js callback, then the app creates a session.
- Actual: Google rejects the request with `redirect_uri_mismatch` before the callback reaches the app.
- Root cause: the exact callback URL used by that deployment is not registered on the OAuth Web client associated with `AUTH_GOOGLE_ID`. This is confirmed by Google's error; access to Cloud Console was not available to confirm which client is selected.
- Code review: `auth.ts` conditionally enables Google when both `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` exist. The current failure occurs at Google's redirect allowlist, before app callbacks run.
- Fix: in Google Cloud Console → APIs & Services → Credentials → matching OAuth 2.0 Client ID (Web application), add the exact reported HTTPS callback. The observed URI is `https://ruanglagi-4m3vkrd4o-bad-code1.vercel.app/api/auth/callback/google`; this came from the error, not a guessed domain. Also add the verified stable production host's callback before using that alias. An Authorized JavaScript origin has only the origin (`https://<verified-host>`, no path); Auth.js uses a server callback, so the exact Authorized redirect URI is the required setting. Do not use wildcards. No code change was made. [Google docs](https://developers.google.com/identity/protocols/oauth2/web-server) require exact redirect matching.
- Regression: not run; requires Google Console configuration and a real OAuth attempt.

#### Payment encryption format and rotation design

- `src/server/security/payment-encryption.ts` uses AES-256-GCM, a 32-byte base64 key, a fresh 12-byte IV, and a 16-byte authentication tag. Ciphertext format is `v1.<iv-base64url>.<tag-base64url>.<ciphertext-base64url>`.
- At the time of the initial audit, `v1` identified the envelope format only and both read/write used one key. A follow-up now retains `PAYMENT_ENCRYPTION_KEY` for `v1` and supports `PAYMENT_ENCRYPTION_KEY_V2` for `v2`; with v2 configured, new writes use v2 while existing v1 values remain readable. The two keys are required to differ.
- Encrypted columns found: `PaymentAccount.accountNumberCiphertext` and `Order.paymentInstructionCiphertext` in `prisma/schema.prisma`. Writers are in `src/server/services/profile-hub.ts` and `src/server/services/orders.ts`; the latter also decrypts account numbers and order snapshots for authorized viewers.
- The version-aware encrypt/decrypt support and synthetic unit tests are implemented. `PAYMENT_ENCRYPTION_KEY_V2` is optional, so deployments without it continue writing v1. After a dual-reader release is deployed, set a distinct staging-only v2 key to exercise v2 writes.
- A bounded resumable re-encryption utility now covers `PaymentAccount.accountNumberCiphertext` and nullable `Order.paymentInstructionCiphertext`. It validates plaintext shape, round-trip decrypts v2 before write, uses ID + old ciphertext compare-and-swap per record, scans in bounded batches, skips already-v2 values, and verifies readability in a second pass. It prints counts and failed entity/record IDs only, never plaintext, ciphertext, or secret values. A rerun retries v1 records; a failed/corrupt value stays unchanged and makes the report fail. Database update exceptions are summarized without driver error detail.
- No production re-encryption or database query was run. Staging project, DB, and storage credentials are unavailable; integration verification is BLOCKED. Do not enable the new key in production until this utility is exercised against isolated synthetic staging data.

#### Isolated staging guard

- `src/server/security/staging-target.ts` verifies the configured HTTPS Supabase project URL and either a direct Supabase PostgreSQL URL or Supabase pooler URL/username against distinct `STAGING_PROJECT_REF` and `PRODUCTION_PROJECT_REF` values. It also requires `SUPABASE_STORAGE_BUCKET` to match `STAGING_STORAGE_BUCKET`, which must differ from `PRODUCTION_STORAGE_BUCKET`. Errors are generic and do not echo URLs or credentials.
- `scripts/verify-staging-target.ts` and `scripts/reencrypt-payment-data.ts` read only `.env.staging.local`; the production-oriented `.env.local` and `.env` are deliberately excluded. `.env*` is ignored by Git. The re-encryption script validates target identity before dynamically importing the Prisma client, so it does not create a DB pool if target checks fail. It requires explicit `--dry-run`, or both `--apply --confirm-staging`.
- Running `npm run staging:verify` in this workspace failed closed because staging/production project refs are not configured. Running the guarded re-encryption command also stopped at the guard. Neither command opened a database connection. Earlier read-only URL metadata inspection found the ordinary local env targets the known Production Supabase project; those values are not used by these staging scripts.
- Set up staging manually in a separate Supabase project. Create an ignored `.env.staging.local` (covered by `.gitignore`'s `.env*` rule) with staging-only `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_STORAGE_BUCKET`, `SUPABASE_SECRET_KEY`, `AUTH_SECRET`, `PAYMENT_ENCRYPTION_KEY`, `PAYMENT_ENCRYPTION_KEY_V2`, and staging `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET`. Use the pooler connection whose username identifies the staging project ref, or its direct `db.<ref>.supabase.co` database endpoint. Configure a separate storage bucket, fresh Auth.js/payment keys, and Google Web OAuth callback `https://<staging-host>/api/auth/callback/google`; Google JavaScript origin is only `https://<staging-host>`. Set non-secret `STAGING_PROJECT_REF`, `PRODUCTION_PROJECT_REF`, `STAGING_STORAGE_BUCKET`, and `PRODUCTION_STORAGE_BUCKET` independently after checking both projects and buckets in the dashboards. Never copy user/payment data from Production.
- To check an isolated configuration without network access: `npm run staging:verify`. After it passes and v2 keys are configured only in staging, run `npm run payments:reencrypt -- --dry-run`. Review the aggregate report; only then use `npm run payments:reencrypt -- --apply --confirm-staging` against staging. Dry-run must report readable values and zero unreadable/failures; remaining v1 values are expected in dry-run. Apply must end with `remainingV1: 0`, `unreadable: 0`, and `failed: 0`. Neither mode has yet been run against a staging database.
- Rollback: retain both v1 and v2 keys and a dual-reader release for as long as any v2 ciphertext exists. An older v1-only release cannot safely read migrated v2 rows. Restoring an old environment value alone does not reverse database ciphertext; no reverse migration utility exists. Production key changes and data migration remain outside this task and require separate approval.
